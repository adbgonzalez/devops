# Unidad: Seguridad en el uso de Docker

## 0. Influencia del uso de contenedores en la seguridad

Los contenedores aportan ventajas significativas desde el punto de vista de la seguridad, siempre que se configuren correctamente.  
No son una capa mágica de protección, pero permiten aislar procesos, controlar recursos y reducir riesgos.

### 0.1. Aislamiento de procesos y recursos
Cada contenedor ejecuta sus procesos, usuarios, red y sistema de ficheros en un espacio de nombres separado.  
Esto impide que un contenedor pueda acceder a otros o al host directamente.

**Beneficio:** si una aplicación es comprometida, el atacante queda “encerrado” dentro del contenedor.

### 0.2. Entornos reproducibles y controlados
Las imágenes son inmutables y versionadas. Permiten repetir despliegues de forma idéntica y auditar configuraciones.  
Esto mejora la **integridad** y la **trazabilidad** de las aplicaciones.

### 0.3. Reducción de la superficie de ataque
Las imágenes minimalistas contienen solo lo necesario para ejecutar la aplicación, eliminando componentes y servicios innecesarios.

### 0.4. Configuración declarativa
La seguridad forma parte de la infraestructura como código. La configuración está en ficheros (`Dockerfile`, `compose.yml`, manifests de Kubernetes), lo que facilita auditorías y revisiones automáticas.

### 0.5. Integración con herramientas de seguridad
El ecosistema Docker/Kubernetes integra herramientas para análisis, monitorización y control:
- Trivy, Grype: escaneo de vulnerabilidades.
- Falco, Sysdig: detección de comportamientos anómalos.
- Vault, Sealed Secrets: gestión de secrets.

### 0.6. Limitaciones y riesgos del uso de contenedores
Aunque los contenedores proporcionan un aislamiento lógico y eficaz, no son una frontera de seguridad absoluta.  
El aislamiento depende del kernel del sistema operativo y de la configuración del daemon de Docker, por lo que existen riesgos que deben considerarse.

#### Container escape
Un *container escape* ocurre cuando un proceso dentro de un contenedor consigue ejecutar **código en el host** o acceder a otros contenedores. Esto puede deberse a:
- Vulnerabilidades en el kernel de Linux o en las interfaces de *namespaces* y *cgroups*.
- Montajes peligrosos, como `-v /var/run/docker.sock:/var/run/docker.sock`, que permitirían controlar desde el contenedor el daemon de Docker del host.
- Contenedores ejecutados con opciones privilegiadas (`--privileged`) o capacidades excesivas (`--cap-add=ALL`).

#### Escalada de privilegios
Docker requiere permisos de administración para gestionar contenedores. Si un atacante obtiene acceso al daemon (`dockerd`), **tiene control total sobre el host**.  
Por ello, no se debe añadir usuarios comunes al grupo `docker` ni ejecutar contenedores como `root` cuando no es necesario.

#### Imágenes y dependencias no confiables
Ejecutar imágenes descargadas de repositorios públicos sin verificación puede introducir *malware*, *backdoors* o vulnerabilidades.  
Es esencial emplear imágenes oficiales, firmadas o revisadas, y realizar escaneos periódicos con herramientas como **Trivy** o **Grype**.

#### Configuraciones inseguras
Otros riesgos comunes incluyen:
- Exposición de puertos innecesarios.
- Montaje de volúmenes con permisos de escritura sobre el host.
- Falta de control en el acceso a secrets y variables de entorno sensibles.
- Falta de actualización en las imágenes base.

**Resumen:** los contenedores facilitan aplicar el principio de *mínimo privilegio*, automatizar revisiones y mantener un entorno más controlado y reproducible.

## 1. Introducción: riesgos y superficie de ataque

### ¿Qué es DevSecOps?
DevSecOps es la evolución natural de DevOps: añadir la seguridad desde el inicio del ciclo de vida.  
No es algo que se añade al final, sino una parte del proceso de desarrollo y despliegue.

"Shift Left Security": significa que la seguridad se incorpora cuanto antes, no cuando el sistema ya está en producción.

### Riesgos comunes en contenedores
| Riesgo | Ejemplo | Consecuencia |
|--------|----------|--------------|
| Imágenes vulnerables | Usar `ubuntu:latest` sin escanear | Exploits conocidos |
| Secrets en Dockerfile | `ENV TOKEN=1234abcd` | Fuga de credenciales |
| Usuario root | `USER root` | Escalada de privilegios |
| Dependencias desactualizadas | `apt install` sin fijar versiones | Paquetes inseguros |
| Exposición de red excesiva | `EXPOSE 0.0.0.0:80` | Acceso no controlado |

### Ejemplo de Dockerfile inseguro
```dockerfile
FROM ubuntu:latest
RUN apt update && apt install -y curl
ADD config.json /root/
ENV TOKEN=1234567890abcdef
USER root
```

## 3. Buenas prácticas en la construcción de imágenes

| Práctica | Descripción | Ejemplo |
|----------|-------------|---------|
| Usar imágenes base minimalistas | Menos superficie de ataque | `FROM debian:bookworm-slim` |
| Fijar versiones concretas | Evita cambios inesperados | `FROM python:3.11-slim` |
| No usar `ADD` sin necesidad | Prefiere `COPY` | `COPY app.py /app/` |
| No ejecutar como root | Crear usuario no privilegiado | `USER appuser` |
| Limpiar *caches* y listas | Reduce tamaño y riesgos | `rm -rf /var/lib/apt/lists/*` |
| Firmar imágenes | Garantiza origen e integridad | `cosign sign myimage:latest` |

## 4. Manejo seguro de *secrets* y variables sensibles

### Buenas prácticas
- Nunca guardar secrets en el Dockerfile ni en variables fijas de la imagen.
- No subir ficheros `.env` ni secrets a Git.
- Usar ficheros externos, variables de entorno o servicios de secrets.
- En `docker-compose`, emplear el campo `env_file` o la sección `secrets`.

### Alternativas
| Método | Descripción | Ejemplo |
|--------|-------------|---------|
| `.env` local | Fichero con variables de entorno cargado externamente | `docker run --env-file .env myapp` o `env_file: .env` en Compose |
| `secrets` en Compose | Guardar secrets en ficheros locales y montarlos en el contenedor | `secrets:` en `docker-compose.yml` |
| Vault / AWS Secrets / Azure Key Vault | Gestión centralizada de credenciales | Acceso mediante API, no incluidas en la imagen |

### Ejemplo práctico con `.env`
**Fichero `.env`:**
```
DB_USER=admin
DB_PASS=SuperSecret123
```

**Ejecución directa:**
```bash
docker run --env-file .env myapp
```

**Versión con `docker-compose.yml`:**
```yaml
version: "3.9"
services:
  app:
    image: myapp:latest
    env_file:
      - .env
    environment:
      - ENV=production
```

### Ejemplo práctico con `secrets` en Docker Compose

**1. Crear el secret localmente:**
```bash
echo "SuperSecret123" > ./db_pass.txt
```

**2. Fichero `docker-compose.yml`:**
```yaml
version: "3.9"
services:
  app:
    image: myapp:secure
    secrets:
      - db_pass
secrets:
  db_pass:
    file: ./db_pass.txt
```

**3. Ejecución:**
```bash
docker compose up -d
```

El secret estará disponible en el contenedor en `/run/secrets/db_pass`.

## 5. Seguridad en ejecución (*runtime*)

### Parámetros seguros en Docker CLI
| Opción | Propósito | Ejemplo |
|--------|-----------|---------|
| `--user` | Evita procesos como root | `--user 1000:1000` |
| `--read-only` | Sistema de ficheros de solo lectura | `--read-only` |
| `--cap-drop=ALL` | Elimina capacidades Linux extra | `--cap-drop=ALL` |
| `--security-opt no-new-privileges:true` | Bloquea escaladas | `--security-opt no-new-privileges:true` |
| `--memory`, `--cpus` | Limita recursos | `--memory=512m --cpus=0.5` |

**Ejemplo CLI:**
```bash
docker run -d   --read-only   --cap-drop=ALL   --user 1000:1000   --memory=512m   --cpus=1   myimage:secure
```

### Versión con `docker-compose.yml`
```yaml
version: "3.9"
services:
  web:
    image: myimage:secure
    read_only: true
    user: "1000:1000"
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
```

**Explicación:**
- `read_only` hace que el FS del contenedor sea de solo lectura.
- `cap_drop` elimina capacidades del kernel.
- `user` define el usuario interno del contenedor.
- `security_opt` aplica restricciones adicionales.
- `deploy.resources.limits` controla uso de CPU y memoria.

## 6. Integración DevSecOps

### Pipeline básico de seguridad con Docker Compose
Se puede automatizar la seguridad combinando construcción segura y escaneo de vulnerabilidades.

**Ejemplo de `docker-compose.yml` para análisis:**
```yaml
version: "3.9"
services:
  app:
    build: .
    image: myapp:latest
    env_file:
      - .env
    read_only: true
    user: "1000:1000"
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true

  scanner:
    image: aquasec/trivy:latest
    command: image myapp:latest
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
```

**Ejecución:**
```bash
docker compose build
docker compose run scanner
```

Si `trivy` detecta vulnerabilidades críticas, la imagen no debería desplegarse.

### Integración en un pipeline CI/CD (ejemplo simplificado)
```yaml
stages:
  - build
  - scan
  - deploy

build:
  stage: build
  script:
    - docker compose build

scan:
  stage: scan
  script:
    - docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image myapp:latest

deploy:
  stage: deploy
  script:
    - docker compose up -d
  when: on_success
```

## Kubernetes
Kubernetes amplía el modelo de contenedores a nivel de orquestación, y con ello también aparecen nuevos retos de seguridad.  
Se verán las principales prácticas para mantener un clúster seguro y controlado.

### 7.1. Autenticación y autorización
Kubernetes emplea dos mecanismos fundamentales:

| Componente | Función | Ejemplos |
|------------|---------|----------|
| **Autenticación (AuthN)** | Verifica quién accede al clúster | Certificados, tokens, integración con OIDC |
| **Autorización (AuthZ)** | Controla qué puede hacer ese usuario | RBAC (Roles y RoleBindings) |

**Recomendaciones:**
- Crear roles específicos por aplicación o equipo.
- Emplear `Role` y `RoleBinding` en lugar de `ClusterRole` cuando sea posible.
- Desactivar la cuenta `default` de los namespaces si no es necesaria.

**Ejemplo básico de Role:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: produccion
  name: lector-pods
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

---

### 7.2. Seguridad de los contenedores

Kubernetes ejecuta contenedores a través de **Pods**, que heredan restricciones del manifiesto y del *runtime* (Docker, containerd...).

**Buenas prácticas:**
- Añadir `securityContext` para definir restricciones.
- Ejecutar como usuario no root.
- Evitar montajes de volúmenes del host.

**Ejemplo:**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-segura
spec:
  containers:
  - name: app
    image: nginx:alpine
    securityContext:
      runAsUser: 1000
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
```

### 7.3. Políticas de seguridad (PSA)

Las antiguas **PodSecurityPolicies (PSP)** fueron sustituidas por **Pod Security Admission (PSA)**, que establece niveles de restricción por *namespace*:

| Nivel | Descripción |
|-------|-------------|
| **Privileged** | Sin restricciones (uso administrativo) |
| **Baseline** | Reglas básicas de seguridad (por defecto) |
| **Restricted** | Máximo nivel de aislamiento (sin root, FS de solo lectura, etc.) |

**Ejemplo de configuración restringida:**
```yaml
apiVersion: pod-security.admission.config.k8s.io/v1beta1
kind: PodSecurityConfiguration
defaults:
  enforce: "restricted"
```

### 7.4. Control de red

Por defecto, todos los Pods pueden comunicarse entre sí. Las **NetworkPolicies** permiten restringir esto.

**Ejemplo: permitir solo tráfico HTTP dentro de un namespace**
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: permitir-http
  namespace: web
spec:
  podSelector:
    matchLabels:
      app: frontend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: backend
    ports:
    - protocol: TCP
      port: 80
```

### 7.5. Seguridad del plano de control y API

**Buenas prácticas clave:**
- Desactivar accesos anónimos (`--anonymous-auth=false`).
- Habilitar auditoría de eventos (`audit-log-path`).
- Restringir acceso al API Server mediante VPN, firewall o IP whitelist.
- Mantener actualizadas las imágenes de los componentes (kube-apiserver, etcd, kubelet...).

### 7.6. Herramientas de auditoría y control

| Herramienta | Uso | Descripción |
|-------------|-----|-------------|
| **kubectl-who-can** | Auditoría de permisos | Lista quién puede ejecutar acciones sobre un recurso |
| **kube-bench** | Cumplimiento CIS Benchmark | Analiza configuraciones inseguras del clúster |
| **kube-hunter** | Escaneo de vulnerabilidades | Busca puertos abiertos y riesgos de red |
| **Falco** | Detección *runtime* | Monitoriza comportamientos sospechosos en contenedores |

### 7.7. Resumen de buenas prácticas

| Área | Recomendación principal |
|------|-------------------------|
| Autenticación | Usar RBAC y eliminar accesos anónimos |
| Contenedores | Usuario no root y FS de solo lectura |
| Políticas | Nivel “restricted” en PSA |
| Red | Definir NetworkPolicies |
| Monitorización | Emplear Falco, kube-bench, logs de auditoría |
| Actualizaciones | Mantener clúster e imágenes actualizados |

**NetworkPolicy: solo tráfico dentro del mismo *namespace***

Esta política limita tanto el **ingress** como el **egress** para que solo puedan comunicarse Pods del mismo *namespace*.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-only-same-namespace
spec:
  podSelector: {}                 # afecta a todos los pods del namespace
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - from:
        - podSelector: {}         # cualquier pod del MISMO namespace
  egress:
    - to:
        - podSelector: {}         # solo a pods del MISMO namespace
```

> 💡 Nota: esto también bloquea el acceso a DNS e Internet. Si se necesita DNS, hay que añadir una excepción para el servicio `kube-dns` en el *namespace* `kube-system`.

**Nivel de seguridad: *baseline* vs *restricted***

- **Restricted (PSS):** requiere *non-root*, `seccomp=RuntimeDefault`, sin *privilege escalation*, FS raíz de solo lectura y sin capabilities adicionales.  
- **Baseline (PSS):** permite excepciones prácticas, como `NET_BIND_SERVICE` para escuchar en puertos <1024.

> **Nivel aplicado:** *Baseline*, ya que Nginx escucha en el puerto **80** como non-root y necesita esa capability.

> Si se cambia el puerto a **8080**, se puede eliminar `NET_BIND_SERVICE` y cumplir el perfil **Restricted** sin otros cambios.
